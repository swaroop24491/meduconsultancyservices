From the logo (brief section 9). Every text colour passes WCAG AA on the backgrounds it is used on. Mustard is never a text colour.

  • --color-tint #edf5ef · icon and number circles

  • --color-border #e6dfd6 · dividers (decorative)

Text, check list and sections

Sections are <section class="section"> with a container. Cream is the base; section--surface (white), section--tint (soft green) and section--deep (deep green, the closing call) are available. Content cards

A .card in a .card-grid is a row: a thin line above (below 1024px only between rows: none under the H2, none after the last row, so the section line stays the one clear break), the h3 on the left and the details on the right from 640px (stacked in split sections from 1024 to 1199px, where the column is narrow). An h3 with a paragraph (registration "What we do") or with a .check-list (service "What we do for you"). A call row is a plain row with a tel: arrow link (home "Want someone to handle it"); no boxed rows. card-grid--columns in a section--stacked shows cards as columns side by side from 960px, each under a short green line, for a few points of equal weight (home "Why businesses choose us"). A column can start with a big green word or number, <p class="col-word">35 years</p>, above its h3 instead of an icon. .section-lead is the one intro line under a section's H2.

Tool parts

Used on the tool pages. The tool scripts (eligibility-checker.js, penalty-calculator.js, contribution-calculator.js) build fields and results with exactly these classes; the markup below is what they output. Page layout: section.tool-section (H1 + .tool-lead), then .tool.tool--split (form left, result and result call box right from 1024px) or .tool-checks (two checks side by side). Inputs sit on cream with the strong border; errors are words, never colour alone. The tool's button is .btn--outline, so it never looks like the call button. Result cards have no red: they are answers, not warnings. A value worked out as you type (the due date) is text in p.field__output with an <output>, hidden while empty, not a read-only box. After the button: a valid result gets focus and scrolls into view; an invalid form focuses the first wrong field (the same in every tool script). Live results that update as you type are not aria-live. No visible H2 inside .tool-section (a visually hidden one where the outline needs it), so the first field stays high on phones. .note is the plain-words disclaimer. .tool-group groups tool cards under a question on the hub. The converter uses ol.tool-steps (numbered H3 steps) and p.tool-status (role="status", the message under the button instead of a pop-up; .tool-status--error for errors).

Header, menu, sticky bar and footer

These are on this page, added by the layout (_layouts/base.html), so every rebuilt page gets them without extra markup.

  • Header: logo, main links, language switch and call button with the full number on desktop. From 769px to 1199px: logo, language switch, call button with the full number and the menu button. On phones (up to 768px): logo, language switch and the menu button only; the sticky call bar is the call button there. The header stays at the top while scrolling (owner change 2026-09-27, replacing D6), except on screens under 421px tall; focus and in-page links scroll clear of it.
  • Menu (phones): call button first, then links, then the language switch. No email. Focus stays inside while open; Escape closes it.
  • Sticky call bar (phones only): full-width call button fixed to the bottom, hidden while the menu is open. The page has bottom padding so it never hides content.
  • Footer: services, places, tools and guides, company links, address, phone and email. The footer is the only place the email appears. No headings in the header or footer.

Structured data (JSON-LD) is added by the layout from front matter: breadcrumb and service (see _includes/schema.html). FAQ JSON-LD comes from faq.html schema=true.

Every tel: link sends a phone_call_click event to Google Analytics with call_location and page_type (decision D5).
